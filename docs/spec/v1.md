# DragonVale Breeding Helper: v1 spec

This is the build spec for v1. It gathers the decisions on [Map: DragonVale Breeding Helper v1 spec](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/1) in one place. Each section links the tickets that decided it; go there for the reasoning and the evidence. Domain terms (Dragon, Element, Route, Valid pair, Breedable now, Available, Breeding cave, Owned forms, …) mean exactly what [`CONTEXT.md`](../../CONTEXT.md) says.

Where this spec and a ticket disagree, the ticket's latest correction wins and this file needs fixing.

## 1. What v1 is

A personal tool, run locally, that answers two questions for a DragonVale player:

- What can I breed right now from the Dragons I own?
- What am I still missing to get the Dragon I want?

It has two parts:

1. **A scraper**, run by hand when new Dragons come out. It reads the DragonVale Fandom wiki's `Data:` JSON pages, downloads the art, and writes a snapshot that gets committed to the repo.
2. **A static web app** that reads the snapshot, keeps the player's Collection in the browser, and fetches one live page (`Data:Limited.json`) for what is limited and available today.

The home screen is a menu of Dragon tiles laid out like the game's Dragonarium. Graphs open from it: a Focus view for one Dragon, or a graph of a whole page or tab.

Nothing in v1 should rule out public hosting later, but v1 is not public.

### Out of scope

- Breeding odds and probabilities. v1 lists possible outcomes only.
- Fetching anything live from the wiki except `Data:Limited.json`. No live image requests either.
- Dragon counts, levels or Traits in the Collection.
- Stars and page completion.
- A "what's new" feature for newly added Dragons.
- Pasting a list of names to mark as owned.
- Player buildings (Weather Station and so on) and event features other than the Event shop list.
- Browser or end-to-end tests.

## 2. Stack and repo layout

Decided in [Tech stack for the scraper and the web app](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/6), with the graph library changed by [Graph nodes reuse the Dragon tile component](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/17).

| Area | Choice |
|---|---|
| App | Svelte 5 + Vite + TypeScript. One static page, no SvelteKit. |
| Graphs | Svelte Flow (`@xyflow/svelte`). Layout by `@dagrejs/dagre`, run in plain TS; Svelte Flow gets positions and does not compute them. |
| Scraper | TypeScript run with `tsx`, in `scraper/`, in the same npm package. `npm run snapshot` runs it. |
| Shared types | `src/lib/snapshot/`, imported by both the scraper and the app. |
| Collection storage | `localStorage`, versioned JSON blob, plus JSON file export/import. |
| Live data | `Data:Limited.json`, fetched from the browser. Fandom sends `Access-Control-Allow-Origin: *` when called with `origin=*`, so no proxy. |
| Tests | Vitest on pure TS logic kept outside the UI. |
| Hosting | A GitHub Pages workflow and Vite `base` set to the repo path, committed but switched off until the tool goes public. |

Paths:

- `public/data/snapshot.json`: the snapshot the app loads.
- The raw `Data:*.json` pages the snapshot was built from, committed next to it, so a snapshot can be rebuilt without fetching again.
- `public/images/`: downloaded Dragon art, Element icons and game icons, under stable file names.
- The snapshot and raw pages are CC BY-SA 3.0 and live apart from the code, which is unaffected by that licence.

## 3. Data sources and licence

From [How to get dragon data out of the wiki](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/3) and [Self-host Dragon images instead of loading them from the wiki](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/18).

- The wiki's `Data:` pages are its own source of truth; editors update them on release day. Dragon pages are a bare infobox built from them, so the scraper never touches HTML.
- One `api.php?action=query&prop=revisions` request fetches the pages the scraper needs: `Data:Dragons.json` (983 Dragons, unique `Name`), `Data:BreedingHints.json` (964 hints), `Data:Game.json` (element list), `Data:Dragonarium.json` (52 pages) and `Data:Limited.json`. Record each page's revision ID.
- Images come from the wiki's `imageinfo` API, batched. `Special:FilePath` returns 403 to scripts, so don't use it.
- Text and data are CC BY-SA 3.0. The art belongs to Deca Games and is not freely licensed. The app hosts its own copies; it never hotlinks `static.wikia.nocookie.net` and never uses other fan sites' image servers (such as the Dragonvale Sandbox's CDN).
- `Module:BreedingSandbox` on the wiki is the wiki's own calculator and documents what each hint field means. Use it as the reference when mapping hints.

## 4. The snapshot

Decided in [Data model for Dragons, Elements and breeding requirements](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/4), extended by [Snapshot and live-data additions for Dragonarium pages, tiles and the Event tab](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/11), [What a new snapshot does to an existing Collection](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/13) and [Self-host Dragon images instead of loading them from the wiki](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/18).

The snapshot holds domain data, not a ready-made graph. The app builds graph nodes and edges at runtime, so a change to how things are drawn never needs a re-scrape.

### Shape

The field names below are the decided ones; exact TS spelling is up to the implementer.

```ts
type Snapshot = {
  meta: {
    schemaVersion: number;   // the app refuses a snapshot it can't read
    revision: string;        // identifies this snapshot; the Collection's snapshotRevision points at it
    source: string;          // wiki URL
    license: "CC BY-SA 3.0";
    pageRevisions: Record<string, number>; // per Data:*.json page
    fetchedAt: string;
  };
  elements: Element[];       // only Elements used by at least one Route
  opposites: [string, string][]; // the 5 pairs, hard-coded in the scraper
  dragons: Dragon[];
  pages: DragonariumPage[];
  renames: Record<string, string>; // old Name -> new Name, cumulative
};

type Element = {
  name: string;
  kind: "primary" | "epic" | "gem" | "legendary" | "mythic" | "rift" | "other";
  icon: string | null;       // local path under public/images/
};

type Dragon = {
  name: string;              // the key everywhere
  wikiPage: string;          // from Alias, else the bare name (Legendary, Mythic)
  rarity: "Primary" | "Hybrid" | "Rare" | "Epic" | "Galaxy" | "Gemstone" | "Legendary" | "Mythic";
  order: number;             // release order
  elements: string[];        // displayed
  breedingElements: string[];// what it adds to a pair's pool as a parent
  isLimited: boolean;
  traits: { kind: "all" } | { kind: "fixed"; element: string } | { kind: "none" };
  canBeParent: boolean;
  image: string | null;      // local path under public/images/, null = silhouette
  routes: Route[];           // one or more
};

type DragonariumPage = {
  name: string;              // from the page's Collection field
  group: "elemental" | "epic" | "special";
  dragons: string[];         // in the game's order
  icon: string | null;
};
```

Left out on purpose: level requirement, breeding time, prices, description, tags, release date, odds, Stars.

### Routes

A Route is one way to obtain a Dragon. A Dragon's **Source** is the set of its Routes' kinds and isn't stored.

```ts
type Route =
  | { kind: "bred"; requirement: Requirement; rift?: "only"; conditions?: Conditions }
  | { kind: "coop"; friendsDragon: string; conditions?: Conditions } // other parent: any Dragon
  | { kind: "evolved"; from: string; decorations: string[] }
  | { kind: "summoned"; artifacts: string[] }
  | { kind: "purchased" };

type Requirement = {        // every field that is set must pass
  parents?: string[];        // 0-2 named Dragons; 2 = exactly that pair
  elements?: string[];       // the pair's combined pool must hold all of them
  minDistinctElements?: number;
  elementOnBothParents?: string;
  anyPair?: true;            // Motley, Dargon
  partner?: "self-or-opposite-hybrid"; // with one name: the other parent is it again or an opposite hybrid
};

type Conditions = {          // badges only; never block anything
  time?: string; weather?: string; alignment?: string;
  parentTrait?: string; namedParentTrait?: { dragon: string; trait: string };
  cloneCave?: string;        // Solis, Lunis
  prerequisite?: string;     // Rigel: own all 22 other Galaxy Dragons
};
```

- `rift: "only"` marks a Bred Route of a Rift dragon. Every other Bred Route can be met by Normal breeding (normal form) or by Rift breeding (Rift form). No separate Rift form Routes are written.
- Galaxy Dragons get Co-op bred Routes. Nebula's hint (`RequiredDragons: ["Nebula"], Any: true`) means a friend's Nebula plus any Dragon.

### What the scraper works out

- **`breedingElements`**: `BreedingElements` if present, else `Elements`, plus the Dragon's displayed epic elements. Unit tests: Sun gives Cold + Lightning + Sun; Rainbow gives the 10 primaries + Rainbow; Gold Olympus gives Earth + Lightning + Olympus.
- **`traits`**: `{Available: "All"}` gives `all` (905 Dragons, normal + Rift form). A fixed `{Default: X}` on a Dragon with the Rift element gives `fixed` (the 37 Rift dragons, including the 10 rift primaries such as Fire Rift). `null` gives `none` (primaries, Legendary, Mythic, Ghostly).
- **`canBeParent: false`** on Gemstone, Crystalline, Legendary and Mythic Dragons. [How dragons without an ordinary breeding route are shown](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/10) counted 29 Gemstone and Crystalline; the scraper should report its count so it can be checked against the wiki. The Shimmering Solstice exception is ignored.
- **Dragons with no hint**: the 9 basic primaries get a Bred Route `{ parents: [itself], partner: "self-or-opposite-hybrid" }` (see Primary Dragons in section 6), plus a Purchased Route. Air has a hint (Water + Fire) and keeps it, plus a Purchased Route. The 10 rift primaries get only a Purchased Route.
- **Evolved** (35, e.g. Ghostly Fire, Wrath), **Summoned** (Kairos, Gaia, Ts'aishen, Bahamut, Tiamat) and **Purchased** Routes come from the hint's evolution and artifact fields and the primaries rule above.
- **`rarity`** is stored as-is, Galaxy included. `Data:Game.json`'s rarity list leaves out Galaxy and is ignored.

### Images

- The scraper resolves every Dragon's `<Name without spaces/punctuation>DragonAdult.png` through `imageinfo` (thumbnail width 120), with a hand-made override list in scraper code for the ~27 that break the convention (Monolith stages, Seasonal, Kairos, …). It downloads each into `public/images/` and stores the local path.
- It does the same for all 35 Element icons (`Icon <Element>.png`), all 52 page icons (`<Name>DragonariumIcon.png`) and the fixed menu icons: `BreedingHeartIcon.png` (Breedable now), `LimitedTimeDragonariumHelpIcon.png` cropped to the hourglass (Limited rotation), `DragonariumBasic.png` (Dragonarium), `BreedingCave2015.png`, `RiftBreedingCave.png`, `CooperativeBreedingCave2015.png` (caves), and the current event's `<EventNameSquashed>DragonariumIcon.png` if one exists.
- A generic event icon ships with the app for events the snapshot doesn't have an icon for.

### Validation

| Problem | Result |
|---|---|
| Unknown hint key or Element name | Fail the run |
| Rarity other than the 8 known | Fail |
| Dragonarium page names an unknown Dragon | Fail |
| Dragon on no Dragonarium page | Warn (search still finds it) |
| Image missing | Warn, `image: null` |

No manual overrides of breeding data. The `renames` map is the one hand-kept file, and it holds only identity mappings.

### Renames between snapshots

From [What a new snapshot does to an existing Collection](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/13). `Data:Dragons.json` has no ID besides `Name`, so the scraper compares the new data with the previous committed snapshot:

- Same `Order` under a new `Name`: a likely rename. The scraper asks the person running it to confirm or reject. It never guesses.
- The run summary always lists removed and added names. When one of each appears in the same run, it offers to pair them as a rename (this catches renames that also changed `Order`).
- Confirmed renames are added to `renames`, which never shrinks and can be edited by hand.

## 5. Live data: `Data:Limited.json`

From [How dragons without an ordinary breeding route are shown](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/10), [Snapshot and live-data additions for Dragonarium pages, tiles and the Event tab](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/11) and [Menu layout on desktop and mobile](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/14).

URL: `https://dragonvale.fandom.com/api.php?action=query&prop=revisions&titles=Data:Limited.json&rvprop=content|ids&rvslots=main&format=json&origin=*`

- Fetched once when the app opens. This is the app's only live request. The game's own servers are never used.
- The **raw** text and fetch time are cached in `localStorage` (versioned). The app parses the raw text on every load, so a parser fix also applies to the cached copy. When running from the cache it shows "Limited data as of <time>".
- The parse is tolerant, because the page is hand-edited and the app can't fail at runtime:
  - Entries that aren't objects or have no `Cost` are skipped (today `islands`, `islandThemes`).
  - The rest match snapshot Dragons by exact name. Names that don't match are listed in a small "Not recognised: …" note at the bottom of the Event tab. No fuzzy matching.
- The parse produces an **overlay**, its own small type:
  - **Limited rotation**: the `dragons` list, each with an end date.
  - **Events**: per event, its name, end date, currency and shop entries (cost, `Breedable`, optional own `countdown`).
- Dates: a Dragon's own `countdown` overrides its event's. An entry whose countdown has passed (after the end of that day, local time) is treated as absent, so a stale cache never shows a dead event. An unparseable countdown means "available, no end date".

What the app derives from the overlay:

- **Available**: a Dragon that isn't limited is always Available. A limited one is Available when it's in the Limited rotation or in a running Event's shop (until the event ends, or its own countdown if earlier).
- **Purchase only**: an Event shop entry with `Breedable: false` (today the debut Dragons, such as Haystack and Sungazer). Its Bred Routes are locked. Known gap: a debut sold only in the regular shop shows as breedable, because the data has no other signal.

## 6. Breeding rules

This is the logic every view shares. Decided in [Focus view rules: what is shown and where it stops](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/5), [How the Collection tracks Rift form](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/9), [Check in game: can Rift-form dragons be parents in Normal breeding?](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/8) and [Menu layout on desktop and mobile](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/14). It's pure TS and covered by Vitest.

### Which owned Dragons count as parents

It depends on the kind of breeding, not on the Owned forms display setting.

- **Normal breeding** (Normal and Co-op caves): any owned Dragon, in normal form or Rift form, Rift dragons included. A Rift form or Rift dragon has to be moved out of the Rift Dimension first, but that's the player's step, not a requirement.
- **Rift breeding** (Rift cave): owned Rift forms and owned Rift dragons only.
- A Dragon with `canBeParent: false` never counts. An owned limited Dragon counts like any other.

### Valid pair

Two parents meet a Bred Route's requirement when every set field passes:

- every required Element is in their combined `breedingElements`;
- any named parents are the pair (two names) or one of them (one name), and with `partner` the other one fits it (see Primary Dragons below);
- the pool reaches `minDistinctElements`;
- both parents carry `elementOnBothParents`;
- `anyPair` passes for any two parents;
- they aren't two opposite primaries (Plant Dragon + Metal Dragon). The opposites are Plant/Metal, Fire/Cold, Earth/Air, Lightning/Water, Light/Dark;
- both can be parents.

Two of the same owned Dragon count as a pair, because the Collection has no counts. An Element being covered by some owned Dragon never proves a Valid pair exists; Seasonal needs Air + Fire + Plant from just two parents.

A Bred Route is **met** when some Valid pair from the parents that count meets it. Conditions (time, weather, alignment, traits, clone cave, prerequisite) are badges and never block.

### Primary Dragons

A basic primary is bred only from one already owned, as in `Module:BreedingSandbox`'s `primary_dragons_rule` (with `Module:Dragon`'s `isOpposite`): one parent is that primary itself, and the other is the same primary again or an opposite hybrid carrying its Element. An opposite hybrid is a Dragon whose Elements, ignoring Rift, are exactly two opposite Elements: Fire comes from Fire + Fire, Fire + Blue Fire or Fire + Frostfire, never from Lava + Plant. So a primary not owned is never Breedable now and has to be bought. The snapshot writes this as `partner: "self-or-opposite-hybrid"` on a one-name Requirement. Air is the exception: it keeps its hint (Water + Fire). Opposite primaries still never pair.

### What each Breeding cave makes

| Cave | Makes | Routes it uses | Parents |
|---|---|---|---|
| Normal | normal forms; no Rift dragons; no Galaxy except Solis, Lunis, Rigel | Bred, without `rift: "only"` | Normal breeding |
| Rift | Rift forms (Dragons with `traits: all`) and Rift dragons | Bred: all of them for Rift forms, `rift: "only"` for Rift dragons | Rift breeding |
| Co-op | everything Normal makes, plus Galaxy | Normal's, plus Co-op bred | Normal breeding; a friend always lends the `friendsDragon` |

A Co-op bred Route is met when the Collection holds any Dragon that counts as a parent. Ordinary Routes completed with a friend's Dragon don't count.

### Breedable now

A Dragon, in the form the chosen cave makes, is Breedable now when:

- it isn't owned in that form;
- the cave uses one of its Routes and a Valid pair (or, in the Co-op cave, the Co-op bred rule) meets it;
- it isn't Purchase only;
- it's Available, if limited.

Evolved and Summoned Routes never count. Owned parents are always usable, so a limited parent only matters once it's missing; then its Route needs it to be Available, as in the Focus view below.

### Basic dragon

For an Element: the Dragon that carries it with the fewest `breedingElements`, ties going to the lowest `order`. Plant gives Plant Dragon; Sun gives Sun Dragon. Nothing is stored for this.

## 7. The Collection

Decided in [How the Collection tracks Rift form](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/9), [Bulk marking and Collection backup](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/12) and [What a new snapshot does to an existing Collection](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/13).

### Shape

```ts
type CollectionBlob = {
  formatVersion: number;     // older versions migrated step by step, newer refused
  snapshotRevision: string;  // the snapshot this was last reconciled against
  entries: Record<string, { normal: boolean; rift: boolean }>; // keyed by Dragon Name
  lastExported?: string;
};
```

- Every entry is always `{normal, rift}`. The checkboxes come from `traits`: `all` shows Normal + Rift form ticks; `fixed` (Rift dragons) and `none` show one Owned tick. A Rift dragon's Owned reads and writes `rift`; a `none` Dragon's reads and writes `normal`.
- When a Dragon gains a Rift form, `normal` stays and `rift` starts false. If a shape change leaves a flag the new shape can't show, the app reads `owned = normal || rift`.

### Loading (and importing)

Each step runs on load from `localStorage` and on import:

1. Migrate `formatVersion`; refuse a newer one.
2. If `snapshotRevision` differs from the loaded snapshot: rewrite keys through `renames`, following chains (A → B → C). If a rename lands on an existing entry, OR the flags together.
3. Set aside **orphans**: names the snapshot doesn't know. They stay in storage, never count as owned or as parents, and exports keep them unchanged. A later snapshot or a newly confirmed rename brings them back.
4. If the Collection was affected, show a dismissible banner once: "Dragon data updated (<date>): 1 renamed (X → Y), 2 entries not recognised [details]". New Dragons aren't announced.
5. Store the new `snapshotRevision`.

### Backup

- The ⋯ menu in the header holds **Export Collection**, **Import Collection**, "Last exported: <date>" (or "never"), and, when there are orphans, "N Collection entries not in current data" with their names and a **Remove them** button. No backup reminders.
- Export downloads `dragonvale-collection-YYYY-MM-DD.json`: the same blob as `localStorage`, orphans included.
- Import replaces the Collection; it never merges.
  1. Validate. Not JSON, not a Collection, or a newer `formatVersion`: show an error naming the problem and change nothing.
  2. Confirm dialog with an explicit warning that the current Collection will be overwritten, a summary ("File: 412 Dragons owned. Current: 398. 14 would change."), and the renames/orphans line ("1 name will be renamed, 2 aren't in current data and will be kept hidden.").
  3. Replace, then show the Undo toast.
- Backups made against a different snapshot are accepted.

### Undo

Every bulk Mark/Unmark, import and orphan removal shows an **Undo** toast. It covers one level, lasts until the next action or a reload, and isn't persisted.

## 8. Screens

Decided in [Prototype the default view and the Focus view](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/7) and [Menu layout on desktop and mobile](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/14). Prototype: [`prototype/menu-layout`](https://github.com/CyberYeti/DragonVale-Breeding-Helper/tree/prototype/menu-layout/prototypes/menu-layout) (layout B; `?phone=1` for the phone layout).

### Desktop layout

- **Left sidebar**, top to bottom (scrollbar hidden):
  - the **Breeding cave** picker: Normal / Rift / Co-op, with the game's cave art;
  - the tabs **Breedable now**, **Limited rotation** and **Event**;
  - the Dragonarium page groups **Elemental / Epic / Special** as an exclusive accordion (one open at a time), listing their pages.

  Every entry shows owned/total.
- **Header**: search over every Dragon, and the ⋯ menu. Search results replace the current tab's tiles.
- **Page header**: the tab's icon and title, a progress bar, owned/total, then **Select**, **▸ Filters**, **▸ Display** and **Graph**. While any filter is on, a row of removable chips ("Filtered: Not owned ✕ …") with Clear all sits under it.
- **Footer**: credits and disclaimer (section 10).

### Phone layout

- The sidebar becomes a ☰ drawer.
- A bottom nav has **Dragonarium** (opens the drawer), **Breedable**, **Limited** and **Event**. In select mode the Mark/Unmark bar replaces it.
- Popovers open as bottom sheets.

### Tabs

- **Dragonarium page**: the page's Dragons in the game's order. There are 52 pages: 10 Elemental, 25 Epic, 17 Special. A Dragon sits on 1 to 4 pages. The Rift page (Special) holds exactly the 37 Rift dragons.
- **Breedable now**: every Dragon Breedable now in the chosen cave.
- **Limited rotation**: the overlay's `dragons` list, each with "ends in N days".
- **Event**: one section per running event (name, icon, end date, currency), each Dragon with its shop cost. With no running event the tab stays and reads "No event", saying in plain words that no event is running. The "Not recognised: …" note sits at the bottom. The event icon is the local copy for that event's name, else the generic one.

### Filters and Display

- **Filters** (▸/▾ button with a count badge): **Breedable now** (in the chosen cave), **Show** All / Owned / Not owned, a **Rarity** checklist (none ticked = all; chips use the wiki's rarity symbols ◖ ◓ ◼ 🟐 🟊 ◆ ▲ ▮), Clear all and Done.
- **Display** (▸/▾): **Owned forms** Either (default) / Normal / Rift, and **Show all Dragons in colour**.
- Opening one popover closes the other.
- There are no Element, Source or Available filters. Dragonarium pages and search cover Elements, the Limited rotation and Event tabs cover availability, and the banners show Source.
- **Owned forms** is display only. It decides which Dragons are shown (Normal hides Rift dragons; Rift shows only Dragons with a Rift form and Rift dragons) and which form counts as owned for colour and the owned/total counts. Either counts either form, except in the Rift cave, where it counts the Rift form. It never changes what is breedable.

### Dragon tile

One component, `DragonTile`, used in the menu, on every graph node, in the popover and in the side sheet.

- Wiki art, or a silhouette when `image` is null.
- Border in the rarity colour from the wiki's `MediaWiki:Dragons.css`, kept in app CSS: Primary `#eeffee`, Rare `#0099FF`, Epic `#8811EE`, Galaxy `#00DDFF`, Gemstone `#FF7711`, Legendary `#EE2200`, Mythic `#FF22BB`. Hybrids have no border, as in DragonVale (the border keeps its width, transparent, so every tile is the same size); the Filters' Hybrid symbol keeps the wiki's `#88ff77`.
- A Rift dragon (its Elements include Rift) carries the Rift Element icon in its top-left corner. Lite tiles leave it off.
- **Grey (greyscale art) = not owned, colour = owned**, per Owned forms. "Show all Dragons in colour" turns greyscale off.
- **Breedable now** = a soft white sheen drifting across the card, always on, held still when reduced motion is on.
- At most one **banner** across the art, the first that applies:
  1. **Summoning only**, **Evolution only** or **Shop only**: no cave can breed it (its only Routes are Summoned, Evolved or Purchased; Shop only is the rift primaries).
  2. **Not available**: limited and not Available.
  3. **Not breedable in <cave> cave**: the chosen cave can never make it (Plumewing in Normal, Fire in Rift).
  4. **Purchase only**.
- Ownership ticks (Normal / Rift form, or one Owned) on the tile toggle the Collection in place. Clicking anywhere else opens the Dragon's Focus view.
- The form a tile opens: the normal form in the Normal and Co-op caves, the Rift form in the Rift cave. A Rift dragon always opens as itself, and a Dragon with no Rift form opens in its normal form. The Focus view has no form switch of its own: to see a Rift form tree, pick the Rift cave.
- **Lite mode** (graphs only): art and rarity border only, no name, banner, ticks or sheen. Far zoomed out, a faded lite tile drops the art and is a rarity-coloured square (grey for Hybrids).

### Select mode

From [Bulk marking and Collection backup](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/12).

- Entered with **Select** or by long-pressing a tile. Every tab and search results have it.
- In select mode, tapping a tile toggles its selection. Ticks are hidden and no graph opens.
- **Select all shown** selects every tile in the view after filters and search.
- The action bar has **Mark** / **Unmark**. With Owned forms Normal it sets normal flags (and the single flag of `none` Dragons). With Rift it sets Rift form flags and Rift dragons' flag. With Either it asks **Normal / Rift form / Both**; single-flag Dragons change only when the choice matches their only form, and Both sets every flag.
- Not available and Purchase only Dragons are selectable like any other.
- The selection clears on leaving the view or select mode.

## 9. Graphs

Decided in [Prototype the default view and the Focus view](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/7), [Focus view rules: what is shown and where it stops](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/5), [How dragons without an ordinary breeding route are shown](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/10), [Click panel layout in the bottom-up graphs](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/15) and [Graph nodes reuse the Dragon tile component](https://github.com/CyberYeti/DragonVale-Breeding-Helper/issues/17). Prototypes: [`prototype/graph-views`](https://github.com/CyberYeti/DragonVale-Breeding-Helper/tree/prototype/graph-views/prototypes/graph-views), [`prototype/click-panel`](https://github.com/CyberYeti/DragonVale-Breeding-Helper/tree/prototype/click-panel/prototypes/click-panel), [`prototype/tile-nodes`](https://github.com/CyberYeti/DragonVale-Breeding-Helper/tree/prototype/tile-nodes/prototypes/tile-nodes).

### Kinds of graph

- **Focus view** (from a tile): the Target's tree on its own.
- **Tab graph** (the **Graph** button, on every tab): the tab's Dragons plus everything they need (Elements, named parents from elsewhere drawn smaller), layered by generation. The Event tab draws one graph for the whole tab.
- **Focusing inside a tab graph**: clicking a Dragon pulls its path into a Target-on-top tree over the faded graph, with shared Element hubs. Tree nodes start at their graph positions and move with a CSS transform transition while the view moves to fit where they are going, with the same duration and easing, as one motion; the tree's edges appear when the move ends. Going back moves the nodes and the view the same way, to the whole graph. With reduced motion (`prefers-reduced-motion`) both jump. Clicking another Dragon re-focuses. Clicking the background or pressing Escape goes back one level: tree → tab graph → tiles. The browser's back (button, mouse, phone gesture) does the same: opening a graph level and changing tab are history steps, re-focusing replaces the step, and a reload lands on the tiles.

- **Arranging**: nodes can be dragged in every graph; edges, edge badges and the background paths follow. A press that moves less than a few px is a click (popover, pulling a tree); ticks inside tiles are never a drag. A **tab graph** (a main graph) remembers its arrangement: the dragged nodes' positions are saved per tab and cave in `localStorage` (`dvbh:arrangement:v1:<tab>:<cave>`, only the moved nodes, by node id, over the automatic layout; ids no longer in the graph are ignored). **Reset arrangement** in the graph header (shown while there are saved moves) forgets them and moves the nodes back to the automatic layout. Moves inside a pulled tree and in a Focus view last only while that tree or view is open.

All graphs are **bottom-up**: Elements at the bottom, the Target or newest generation on top. Graphs follow the chosen cave (Rift cave draws Rift breeding) and ignore the Show, Rarity and Breedable now filters.

### Nodes and edges

- **Dragon nodes** are `DragonTile`, with the same greyscale, sheen, banners and ticks as the menu.
- **Element nodes** show the game's Element icon. Covered (some owned parent carries it) or missing is display only and never decides where a view stops.
- **Route pills** (◆) join a Dragon to what one of its Routes needs. A `minDistinctElements` or `anyPair` requirement is a single rule node ("Any 4+ elements", "Any pair").
- **Edges** are drawn exactly as the requirement is written. Pairs, suggestions and the basic dragon are never drawn.
- **Edge kinds and badges** (HTML via `EdgeLabel`):
  - evolves-from, with a badge naming the decoration;
  - Co-op only, from a duplicate node "<Dragon> (friend's)", labelled "+ any dragon" (a label, not a node);
  - 🔒 Purchase only;
  - condition badges (time, weather, cave, alignment, trait, prerequisite such as Rigel's);
  - "No valid pair yet" when every Element is covered but no Valid pair exists;
  - a Route that names its own Dragon (a basic primary's) draws no edge from that Dragon; its pill says "Breeds only from Fire + Fire or a Fire/Cold hybrid" instead;
  - "Not available" (see rule 6 below).

### Focus view rules

The Target is a Dragon plus form. For a Rift form Target, and for `rift: "only"` Routes, only Rift breeding parents count.

1. **Every Route of the Target is shown.** Met ones are highlighted. Purchased and Summoned are badges on the Target, not branches.
2. **A Route is met** when a Valid pair from the Collection meets it (section 6).
3. **Expansion**: only missing named parents expand, recursively through their own Routes. A branch stops at a Dragon owned in the right form, at a dead end (Summoned, Purchased, the friend's node), or at a Dragon already in the view, which draws an extra edge instead (this handles cycles such as the Chrysalis family). No depth limit. Element nodes are always leaves.
4. **Evolved**: the evolves-from edge leads to the base Dragon, which expands as normal.
5. **Purchase only Route**: shows its parents but doesn't expand them.
6. **A missing limited parent that isn't Available**: the Route is dimmed with a "Not available" badge. Selecting it shows the path at full brightness with that Dragon locked, and its branch keeps expanding, because it may be obtainable another way.
7. **Targets that can't be bred**: a Summoned Target gets a dead-end badge; a Target that isn't Available is dimmed; there's always a line saying why the Target can't be bred now.
8. **Owned Target**: shown the same way, with an "Owned" banner.
9. The friend's duplicate node is never checked against the Collection and never expanded. A Dragon that can't be a parent never appears as one.

### Click panel

Tapping a Route, Element or Dragon node opens it. One panel-data function feeds both renderings.

- **Popover** (default), attached with `NodeToolbar` next to the node; docked at the bottom on a phone. A headline ("✔ Met · 1,396 Valid pairs", "No Valid pair yet", "Not met"), the reason, and the top 3 pairs or suggestions.
- **Details** on the popover opens the **side sheet** (a bottom sheet on a phone) with everything:
  - a met Route: the owned Valid pairs, grouped by parent (simplest first) and searchable;
  - a Route with no Valid pair yet: the reason (e.g. "Plant Dragon + Metal Dragon are opposites") and suggested Dragons that would make a Valid pair with something owned;
  - an Element: the owned Dragons that carry it, then the basic dragon, then the alternatives;
  - ownership ticks on every Dragon listed.
- Suggestions never include the Target. Order: Breedable now first, then Available, then not Available; then the basic-dragon order.
- Tapping a Dragon named in a panel selects its node if it's in the tree, otherwise makes it the Target. The edges into a selected Route are highlighted.

### Performance rules

Measured in the tile-nodes spike: naive Svelte Flow manages 3 fps zooming the 983-tile stress graph; with these rules, close-up panning holds 55 to 60 fps. Apply them to large graphs (big pages, Event, tab graphs with a pulled tree):

- `onlyRenderVisibleElements` on.
- Faded background tiles and far-zoom tiles use lite mode; far zoomed out, faded tiles drop the art.
- Faint background edges are one merged SVG path behind the nodes (`ViewportPortal`). Only lit edges (the tree's) are real Svelte Flow edges.
- Effects that read the viewport (`screenToFlowPosition`, `getViewport`) use `untrack`, or every pan frame rebuilds every node.
- Animated fits set the viewport from the laid-out boxes (`setViewport`), not with an animated `fitView`: that stays queued for the whole transition, and each node mounted on the way restarts it, so it crawls and stops short.
- A drag doesn't rebuild the nodes: only the dragged node's background edges are redrawn per frame, and the saved position is applied once on drop.

## 12. Known gaps

Accepted for v1, not bugs:

- Traits aren't tracked. The 17 trait hints (e.g. Kampos needs a Water-trait parent) and the 4 rift-alignment hints are badges only.
- Conditions (time, weather, cave) never block.
- A debut sold only in the regular shop shows as breedable.
- The data has no history of limited windows, so "Not available" only knows about today.
- A new event's icon is generic until the next snapshot.
